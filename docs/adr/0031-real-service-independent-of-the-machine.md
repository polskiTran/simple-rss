# Test the real service on disk, independent of the machine running it

Server tests run the complete service, not a model of it. `tests/support/boot-service.ts` `bootService` starts it on a free port with a real socket, real migrations and a real SQLite file in a directory from `tests/support/temp-dir.ts` `makeTempDataDir`, with upstream HTTP answered by fixtures. The database is never in memory, so WAL files, file permissions and durability behave as they do in the container; `tests/server/health.test.ts` reads the absent `-wal` file as proof that the service closed its last connection, which an in-memory database cannot show. `bootService` imports no test framework, because both the Vitest harness and the Playwright `installation` fixture in `tests/browser/installation.ts` wrap it, and each owns its own teardown. The Vitest harness has two entry points, because a failed startup has no database, no settings and no scheduler: `startTestService` fails the test unless every boot, restarts included, comes up ready, and its handle carries `database`, `settings`, `wakeScheduler` and `restart`; `startUnreadyTestService` fails the test unless startup fails, and its handle has none of them, so a failed-startup test reads `/health/ready` and the logs, and `tsc` refuses anything else. A test builds a module by hand only for a state no request can arrange: the credential rotation races in `tests/server/auth/authentication.test.ts` need a `PasswordHasher` that holds verification open between two requests. Client tests answer the API through `tests/client/stub-api.ts` `stubApi`, whose `Answers` map types each route's success body from `src/shared/api.ts`, so a fixture that drifts from the contract fails `pnpm typecheck` instead of rendering a screen that did not load; an `undefined` answer is a route that responds with no body. The cost is speed: every server test pays for a temporary directory, migrations and a socket. The rejected alternatives are an in-memory database, which hides exactly the file behaviour the container depends on, and mocks of internal modules, which pin how the service is built rather than what it answers.

No assertion may depend on the timezone or clock of the machine running the suite. The server harness drives time with `ManualClock`. `playwright.config.ts` sets `timezoneId: 'UTC'`, because claiming an installation seeds its timezone from the browser and the Digest groups days in that timezone. The Add feed tests in `tests/client/feeds.test.tsx` fake `Date` at noon UTC on the fixtures' day, 2026-08-08, so every previewed instant is a whole number of days away in any timezone. The cross-origin specs need no second host: the `foreign` fixture serves from `localhost` while the installation listens on `127.0.0.1`, and a browser treats those as different origins even on the same port.

Client tests run under jsdom, and `tests/client/setup.ts` fills its gaps with stand-ins that are faithful for this client rather than general polyfills. `PointerEvent` is `MouseEvent`, because Base UI's radio passes a press to its hidden input as a `PointerEvent` and a `MouseEvent` carries everything that press needs. `Element.prototype.animate` returns an animation that has already finished, and `matchMedia` never matches, because the client's motion animates DOM that is already in its final state, so skipping the animation leaves the same DOM. Two gaps are handled where they occur: under jsdom `import.meta.url` is an `http:` URL, so `tests/client/design-foundation.test.ts` resolves `src/client/styles.css` from `process.cwd()`, and jsdom cannot perform a real navigation, so the click probe in `tests/client/shell.test.tsx` calls `preventDefault` after recording what it saw. Anything that needs real layout, real navigation or real motion belongs in `tests/browser/`.

Vitest's 5s default timeout holds for every test, and a test that comes near it removes the slow work instead of raising the budget. A long password is pasted, not typed: typing two 400-character passwords in `tests/client/authentication.test.tsx` uses most of the 5s on a CI runner. The first Reader article lazy-loads the Markdown renderer (`views/reader-view.tsx` `preloadArticleMarkdown`), which can take over a second in a loaded suite, so `tests/client/reader.test.tsx` waits up to 5s for the article's heading rather than the 1s default of `findByRole`. One test raises its timeout, to 20s: the 20,001-item list in `tests/server/ingestion/feed-content.test.ts`, whose delivery re-parses the stored Markdown in quadratic time. That cost is the product's, not the test's, and the raised timeout stays only until delivery is made linear.

`pnpm dev` runs Vite on 5173 and proxies to the server on 8080. The proxy keys in `vite.config.ts` are regular expressions anchored on a path segment (`^/api/`, `^/health(/|$)`), because a plain `/api` prefix also matches the client's own `/api.ts` module and would send it to the backend. Each target is an object with `changeOrigin: false`, because Vite expands a string target to `changeOrigin: true`, which rewrites `Host` to 8080 while the browser's `Origin` still names 5173, and `http/same-origin.ts` `sameOrigin` would then refuse every unsafe method. The verification instance in `.claude/skills/verify-simple-rss/scripts/vite.verify.config.mjs` removes the proxy entirely, so a request the dev mock does not answer cannot reach the developer's server.

**Amended by ADR 0033.** The Markdown renderer is now loaded by `screens/reader-screen.tsx` `loadArticleMarkdown`.
