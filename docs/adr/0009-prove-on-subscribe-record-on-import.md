# Prove a Feed inside the subscribe request; record an OPML Import before its first retrieval

Subscribing proves the Feed inside the request. `POST /api/feeds/preview` retrieves and parses the URL the User typed, follows the first Declared Feed when the answer is an HTML page and returns the rest, and records nothing. `POST /api/subscriptions` takes the Feed URL the preview settled on, retrieves and parses it again, and records Feed, Subscription, and Feed Window in one transaction. It answers 201 with a Subscription that is already `available` and whose items are already in the Digest, or 4xx naming why the URL did not prove to be a Feed. A Feed that never answered leaves no row. OPML Import keeps recording first: every entry is recorded without contacting its Feed, begins unchecked, and is retrieved by the scheduler on the ordinary poll path. `unchecked` therefore survives as a Feed Availability state, but only import produces it.

The two differ because their inputs differ. Subscribe is one URL the User is looking at, pasted a moment ago. It may be a page rather than a Feed, and it may be wrong. The honest answer is the Feed itself, its title, its host, its last five items, with the question `subscribe to <title>?` asked before anything is written; the honest failure is one sentence under the field while the User is still there. Proving costs one request. Measured against a 100 KB Feed from the sandbox, retrieval is 82 ms and parsing 41 ms, and a subscribe reaches `available` in 274 ms on an idle installation. What made a new Subscription look stuck was never that cost but the scheduler state `unchecked` hid from the User: a nudge coalesced behind a running drain of up to 25 Feeds, a `busy` retrieval gate recorded as a full Polling Interval's deferral, a first failure backed off two hours. Import is a list of URLs that are Feeds by construction, because another reader already retrieved them, and nobody is looking at any one of them. Proving each inside the request, which the reader once did, held one HTTP request open while 136 Feeds answered, made a Subscription's existence depend on every remote server answering within one attempt, and left no row for a Feed that failed once, so nothing could ever retry it. Recording first makes the existing backoff and availability machinery the retry story, at the cost of admitting Feeds nobody has ever reached. That is the right trade for a list and the wrong one for a single URL.

ADR 0007 drew two consequences from recording first, and this decision narrows both to import. The first is the quiet merge at retrieval: a first retrieval that reveals an already-subscribed Feed behind a different URL folds the later Subscription into the existing one, deleting nothing retained. It survives for import alone, because import is the only path that records a URL before seeing where it resolves. Subscribe learns the resolved URL before it writes, so duplicates are settled inside the request by one rule: the alias owner of the resolved URL is the Feed, and it is either subscribed (409), dormant with its row retained for Library attribution (revived, with the Feed Window and the new `subscriptions` row in one transaction), or unknown (created). The preview itself never refuses a duplicate; it answers `subscribed` and the dialog offers to open the Feed. The second consequence, a never-succeeded Feed retrying forever on the ordinary backoff, still holds, but only import can make such a Feed. Import also gains what this effort learned about the scheduler. A deferral, meaning a `busy` gate or a cancelled attempt, is rescheduled for the next wake, a minute away, rather than a full Polling Interval, since a deferral says nothing about the Feed. Preview and subscribe run under their own Retrieval operations (ADR 0005), a discovery profile that accepts `text/html` under a 1 MiB ceiling and a preview gate separate from the `feed` gate, so a running import drain can neither refuse nor starve the dialog. Nudge coalescing stays as it is: an import's nudge joining a running drain and earning one more is right for bulk work, and subscribe no longer goes through the scheduler at all.

Three costs are accepted. A subscribe makes two publisher requests, the preview and then the subscribe, a conditional one where the publisher sends validators, rather than caching the preview; a cache would be a second place a Feed's state lives. A subscribe takes as long as the publisher takes, under a 15 s deadline, where it used to return in 17 ms. And the escape hatch that ADR 0007 amounted to, add it anyway and let the first check decide, is gone for subscribe: a URL that does not prove to be a Feed is not a Subscription. The rejected alternative is one record-first path for both callers with a faster scheduler behind it. The scheduler's latency can be trimmed, and this effort trims it, but a record-first subscribe still cannot ask `subscribe to <title>?` before committing, still cannot tell the User which of a page's Declared Feeds they are about to add, and still turns a mistyped URL into a row that retries forever.
