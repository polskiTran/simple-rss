# Read Feed documents as publishers write them, and key each Feed Item on the identity least likely to change

Publishers get RSS and Atom wrong in a handful of recurring ways, and `ingestion/feed-document.ts` `parseFeedDocument` reads each of them for what the publisher meant. A Feed that declares its own Feed URL as its site, the `rel="self"` mistake, has declared no Feed Home Page, because linking to it would send the User back to the XML. The match is loose and covers every URL the Feed was reached by: `pageKey` compares host, path without a trailing slash, and query, ignoring the scheme, and `priorUrls` adds the entered and requested addresses to the post-redirect one. A Feed that moved is likely to still name the URL it was pasted from, over `http`, with a trailing slash, or from before the redirect that leads to it now. An RSS `guid` is a permalink unless `isPermaLink` says otherwise, and it serves as the Feed Item's link when the item declares none, but only when it is an absolute `http` or `https` URL on its own: resolving an opaque id against the Feed URL would turn it into a link to nothing. The Discussion comes from RSS `<comments>`, the form Hacker News and Lobsters use, or from an Atom `replies` link (RFC 4685) whose type is HTML or absent; a Discussion on the item's own page is dropped, because WordPress points `<comments>` at the item's `#respond` anchor and so declares nothing new.

Relative URLs in Feed Content resolve against the nearest declared `xml:base` first, then the item's link, then the post-redirect Feed address; the item's own link, image, and Discussion resolve against the nearest `xml:base` or the Feed address. A declared `xml:base` nests on the one it inherits and becomes the base for links as well (`ingestion/feed-content.ts` `withXmlBase`); a Feed document starts with no link base of its own so that the item's link can supply it, and an `xml:base` that is not a valid URL is ignored rather than failing the item. Text fields that may carry markup (titles, descriptions, summaries, content) are parser stop nodes and arrive as raw XML text, so `decodeXmlText` unwraps each CDATA section verbatim and entity-decodes only the text outside it, and escaped HTML is decoded exactly once.

A Feed Item's identity is its `guid` (Atom `id`), else its link, else a SHA-256 fingerprint of its title and publication time. The fingerprint leaves the summary out because publishers correct summaries more than anything else, and hashing the summary would turn each correction into a new Feed Item instead of an update. Seeing an item again corrects its mutable metadata, its title, link, Discussion, publication time, image, summary, and Feed Content, through the upsert on `(feedId, dedupeKey)` in `ingestion/feed-window.ts` `persistFeedWindow`; its identity, its first-seen time, and its Library membership never change. `persistFeedWindow` writes inside the caller's transaction, and the caller has already confirmed in that transaction that the Feed is still subscribed.

Conditional requests keep the validators the publisher last sent. A 200 stores `ETag` and `Last-Modified` exactly as received, absence included, so a validator the publisher stopped sending is never replayed. A 304 may still carry new validators: `subscriptions/feed-poll.ts` stores whichever it carries, keeps the stored ones otherwise so later requests stay conditional, and touches no Feed Item.

OPML is read and written with the same tolerance. Exporters disagree on attribute casing, `xmlUrl` and `XMLURL` both occur, so `subscriptions/opml.ts` matches attribute names case-insensitively. Export writes each Feed's resolved URL, the endpoint where its redirects currently end, rather than the URL the User entered.
