# Serve the Digest and the Library in keyset pages over the computed chronology

`GET /api/digest` and `GET /api/library` answer fifty Feed Items at a time, resumed by an opaque cursor rather than an offset. Polling inserts at the top of the chronology, so any offset drifts between requests — the same page number repeats or skips items — while a keyset cursor ("strictly older than this instant, ties below this id") is unmoved by arrivals above it. The catch is that the chronology is not a column: it is the fallback rule in `src/server/digest/chronology.ts` (publication time, unless missing or implausibly future, then first-seen). A bounded page therefore has to state that rule in SQL before the `LIMIT`, because sorting in JavaScript after a naive `LIMIT` would bound the wrong fifty. `DigestService.after()` answers the Reader's `next in the digest` from the same keyset query, which is also what keeps it correct across page boundaries.

Two deliberate acceptances: the cursor's internals (chronology instant, item id) never enter the API contract, so the encoding can change without a client migration; and because the implausible-future horizon moves with the clock, an item published up to a day ahead can cross a held cursor and be seen twice or missed once — tolerated as a rarity rather than paid for with horizon pinning. Page size is a server constant, not a parameter: no caller has a reason to differ, and changing it later is one number. The Feeds list stays whole — it is bounded by curation at the ~100-Subscription target, not by Retention.

**Amended (Library order).** The Library now pages by when each item was saved, not by the chronology: the Saved screen groups by the month of the save and sorts newest or oldest save first (`?order=oldest`). The keyset is the same shape — an instant and a tie-breaking id, strictly beyond the cursor — over `library_items.saved_at`, a stored column, so the SQL-before-`LIMIT` concern above does not arise there. A save is not moved by polling, so nothing drifts between pages; a cursor carries no order, and continues whichever order the request names.

**Amended (Digest filters).** The Digest now narrows by the Rhythm of its Feeds, by one installation-timezone day, and by chosen Feeds (`?rhythm=`, `?day=`, repeated `?feed=`). Each is one more condition in the same `WHERE` as the keyset, so the cursor pages under any of them unchanged: it still names an instant and an id along the chronology, and a request continues whichever filter it names. Each page's groups carry their day's whole count under the same filter, counted by a separate query over the page's days — a page cut mid-day no longer leaves its count unknown.

**Amended (Digest in whole days).** The Digest no longer pages by an item cursor. Its reading is a day at a time — each Feed's items that day in one box, folded past five, under chips counting the day's Feeds — and a page cut mid-day would split a box and leave its fold and chips wrong. So a page is whole installation-timezone days, newest first, as many as it takes to reach fifty items: the query takes the first fifty along the chronology as before, then completes the day the fiftieth falls on. The next page starts `from` the next older day with items (`nextFrom`), the same `?from=` a day picked on the calendar uses — that day and every one before it — so paging and picking a day are one request. A day key is as unmoved by arrivals above it as the cursor was. What this accepts: a busy day comes whole however long it runs, where fifty was a ceiling before. The Rhythm and chosen-Feed filters are gone with the Digest's Rhythm switch — folding and the day's chips answer the busy Feed they were for — and so is the separate day-count query, since a whole day counts itself. The Reader's `after()` keeps the keyset query, and the Library keeps its cursor.
