# Back up with VACUUM INTO, and restore only into an empty data directory through a verified staging copy

`simple-rss backup <destination>` writes a snapshot of the live database with SQLite's `VACUUM INTO`, never a file copy. `VACUUM INTO` produces a compacted, transaction-consistent copy even while the server is running and the WAL holds writes the main file does not have yet; copying the files of an open database can capture the main file and the WAL at different moments, which is a corrupt backup. The snapshot is written to `<destination>.partial` and renamed into place only once complete, and an existing destination is refused, so a backup never overwrites anything and a failed one leaves no file that looks finished.

`simple-rss restore <backup>` only initializes an empty data directory. It refuses a directory that already holds a database, and it also refuses one that holds only a stray `-wal` or `-shm` file, because SQLite adopts the sidecars it finds next to a database, and an old WAL would be replayed over the restored contents. Every check runs on a staging copy, `<database>.restoring`: the integrity check, the migrations this release needs, a rebuild of the search index, and a real write. The staging copy is renamed onto the live path only after all of them pass and it has left no sidecar behind, so a restore that fails at any step leaves the live path untouched. The search index rebuild is passed in as a dependency (`rebuildIndex`) rather than imported, because it must run on the staging copy before the rename, while the derived index belongs to `search/` and `persistence/` does not depend on it.

The CLI dispatches `backup` and `restore` before it opens the live database, and every other command opens it and applies migrations first. Opening a path creates an empty database there, which is exactly what `restore` must refuse to find and what `backup` must not mistake for a real one. Each command writes its result to stdout, as one JSON object where there is a result to report, and anything it logs goes to stderr. stdout is the command's result channel, and a log line interleaved with the JSON report would break piping it to `jq`.
