# Retrieve the outside world through one hardened boundary

Feed polling, Reader extraction, and the image proxy all retrieve through a single boundary in `src/server/upstream` rather than calling `fetch` where they need bytes. The boundary owns the rules that make an outward request safe — HTTP and HTTPS only, no credentials in the URL, no localhost, private, reserved, or self-referencing destination, every redirect destination revalidated independently within five hops, one deadline covering resolution through the last byte, a decoded-byte ceiling enforced while streaming, a content-type allowlist, bounded concurrency with a bounded queue, and a fixed set of failure categories — and callers choose the limits without being able to skip a check. It takes a URL the installation already decided to retrieve and exposes no arbitrary-URL proxying.

Two consequences are deliberate. Address validation happens inside the DNS lookup the socket itself uses, in a Node `http`/`https` client rather than `fetch`, because validating a name and then handing it to a separate resolver leaves a window in which the answer can change; that client also decodes compressed bodies so the ceiling counts the bytes the process will actually hold, and never follows a redirect itself. And the transport stays an injected `HttpClient`, so tests declare what a publisher returns — including slow, oversized, lying, and redirecting ones — without reaching the network, while the resolver is injected alongside it so a moving name is equally testable.

The cost is a hand-written HTTP client to maintain and a boundary that must be threaded to each retrieving module. The alternative — per-caller `fetch` with shared helper functions — was rejected because helpers are opt-in: one later ticket forgetting one call is an SSRF, and the reader would have no single place to answer for what it is willing to retrieve.
