# Tell the User whether the server answered, and read a screen again only when its key changes

Every failed request the client makes is one of two kinds, and the User is told which. `api.ts` `failureKind` calls a failure `unreachable` when `fetch` rejected (a `TypeError`) or the client's own deadline ran out (a `TimeoutError` from `AbortSignal.timeout`, 30 seconds, 60 for the Reader View): no answer arrived. Everything else is `unavailable`: a refusal the server sent, or a body that is not JSON or fails its schema, came from the server, and what it said is wrong. The gate says "Can't reach simple" and asks the User to check the connection for the first, and "simple isn't available" for the second (`app.tsx` `Unanswered`); every screen's `LoadFailure` says "can't be reached" or "didn't load". The split exists because the two ask different things of the User: a connection is theirs to fix, a failing server is not. The Add feed dialog applies the same rule to blame (`feed-language.ts` `addFailure`). A request the server never answered is the server's failure, "The reader is unavailable. Nothing was added.", not the publisher's, unless the client's deadline ran out, which counts as the publisher's timeout because the server was waiting on the publisher. Only an address that is no address and a Feed already subscribed offer no Retry; any failed retrieval may answer next time.

A screen reads the server through `use-resource.ts` `useResource`, which reads again only when its `key` changes or on `retry()`. `load` is called through `useEffectEvent` and may close over anything, so the key is the whole statement of what makes a read stale. The cost is that this is a contract the type system cannot check: a caller that leaves something out of the key shows a stale screen rather than looping on requests. Leaving the view, a new key, or a retry aborts the read in flight, and an answer whose signal was aborted is dropped, so a slow answer never overwrites a newer one. While a new key loads, the previous value stays in view as `loading.previous`, which is how the Digest keeps the day on show until the next one answers (`docs/DESIGN.md` §7). `dropOnNewKey` opts out where the previous value would be wrong under the new key: an opened Feed never shows the Feed opened before it. `usePagedResource` tags each Show more with the load it extends and drops a page that arrives after a reload or retry has replaced that load.

Saving to the Library shows before the server answers. `components/save-toggle.tsx` `SaveToggle` shows the new state on the press through `useOptimistic`; a failure returns it to the state it had and reports through the App's save failure line (`docs/DESIGN.md` §5 Notices), since a row or toolbar has no room for a sentence and the toggle may have left the screen by the time the failure arrives.
