# Keep keyboard focus in drawn order and announce every answer

Focus follows what is drawn, by DOM order rather than `tabindex`. `docs/DESIGN.md` §5 says the header is focused in the order it shows; `components/section-nav.tsx` `SectionNav` renders the Digest and Feeds switch, then its children, which are the search line, then Saved and Settings, so the DOM is that order. A screen's toolbar is portalled into the chrome (`components/chrome-toolbar.tsx` `ChromeToolbar` into `ChromeToolbarSlot`), after the header, so the stylesheet alone places it: a row under the header on desktop, and within the phone's top bar after the search square. At either width it is focused after the header, where it is drawn.

Headings and sections take focus only by script: a screen's heading on arrival so the change is announced (`docs/DESIGN.md` §5 Arriving), and a section a jump carries the keyboard into (`components/group.tsx` `enterSection`). They are not controls, so they draw no focus ring (`:is(h1, section)[tabindex='-1']:focus-visible`). WebKit would otherwise draw one: after a mouse click nothing is focused, and WebKit treats the script's focus as keyboard focus. Save in a list is revealed when its item has `:focus-visible` inside it, not `:focus-within`, because a click leaves focus on the word and would keep it showing after the pointer has left. Save's accessible name starts with the word on screen, "Save" or "Saved", then the item's title, so a User of voice control can say what they see.

An action's answer is one line in an `aria-live` region (`docs/DESIGN.md` §5 Notices). Each action on the Feeds and Feed screens clears its notice before its transition starts, outside the transition so the clearing renders at once. Two behaviours rest on that. An answer repeated word for word is announced again, because the live region sees the line empty and then filled. And the line leaves `display: none` (`.note:empty`) and mounts again, so the stylesheet's `@starting-style` fade plays for each answer. A notice set without clearing first would announce and fade only the first time.

A form's submit is never disabled before it is pressed (`docs/DESIGN.md` §5 Gate). What a press finds wrong is `password-failure.ts` `Feedback`: a reason that belongs to one field, or a note about the whole form. A field's reason is shown on that field, which takes focus, and editing the field clears it (`afterEdit`), since the edit answers it. A note stays until the next submit, since no edit answers it: a lost connection, too many attempts, or on Setup a Setup Secret missing or too short in the deployment, which is the operator's to fix. Sign in, Setup and the password change share this. In the Add feed dialog, Enter in the address field proceeds itself (`views/add-feed-dialog.tsx` `keyDown`), because a browser form submits on Enter only through an enabled submit button, and Subscribe stays disabled until a Feed is chosen.
