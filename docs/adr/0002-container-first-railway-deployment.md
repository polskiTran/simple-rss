# Use a container-first Railway deployment

Package the static client, API, in-process feed scheduler, server-side Reader View extraction, and SQLite access as one portable Docker service, with Railway and one persistent volume as the documented managed deployment. This costs slightly more than Fly.io but minimizes setup and operations; the single-instance and brief deployment-downtime constraints are acceptable for a single-user reader, while the generic image preserves the option to move to another container host.

**Amended (configuration and build layout).** Configuration comes from the environment and is parsed once at startup (`loadConfig` in `src/server/config.ts`). An empty variable counts as unset, because a platform often delivers a variable that was cleared as an empty string, and Zod's `.default()` applies only to an absent key; dropping empty values lets the defaults apply. The build puts the server at `dist/server/` and the client at `dist/client/`, and both paths are resolved from the module's own location rather than the working directory. The default client directory is `../client` from the server module, which serves `pnpm start`; the image sets `CLIENT_DIR` and `DATA_DIR` explicitly. The version the server reports in `/api/meta`, the JSON export and the outbound User-Agent is read once from `package.json`, two levels above both `src/server/` and `dist/server/`, so the image must ship `package.json` beside `dist/`.
