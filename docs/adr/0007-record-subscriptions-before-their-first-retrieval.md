# Record Subscriptions before their first retrieval

Subscribing and OPML Import record the Subscription and return without contacting the Feed. A Subscription therefore begins unchecked — no retrieval has ever happened — and that is an ordinary Feed Availability state, not an error or a provisional phase. First retrievals are scheduler work like any poll: a new Subscription is due immediately, subscribe and import nudge the scheduler awake, and a tick that fills its batch runs another at once so a bulk import drains at the pace of the retrieval gates rather than the wake interval. The subscribe UI briefly watches for the first outcome so a mistyped URL is still caught in one sitting, but the server never promises it.

The rejected alternative — validating each Feed against the network inside the request, which the reader originally did — made a Subscription's existence depend on a remote server answering within one attempt: a 136-feed import held one HTTP request open for many minutes, and a Feed that failed once left no row, so nothing could ever retry it. Recording first means the existing backoff and availability machinery is the retry story, at the cost of admitting Feeds nobody has ever reached. Two consequences follow: a never-succeeded Feed retries forever on the ordinary backoff, since Feed Availability refuses to imply removal; and duplicates hidden behind different entered URLs are only discovered at retrieval, where the duplicate Subscription merges quietly into the existing Feed — deleting nothing retained, so a duplicate with items goes dormant like any unsubscribed Feed and Retention judges what remains.
