# Let append-only migrations own the schema, with Drizzle as query-side typing

The database schema is whatever the migrations in `persistence/migrations.ts` create, applied in order at startup. Each migration has a version that is 1-based and contiguous, and once a migration is released its version, its place in the list and its SQL never change. A released migration that is wrong is corrected by a new migration. The ledger `schema_migrations` records which versions a database has, and an installation upgraded from any earlier release runs exactly the steps it is missing, so editing a released migration would leave existing databases with a schema no fresh one has. Each migration runs in its own transaction with its ledger row, so a failure leaves the database at the last complete version and the next start retries from there.

A database whose newest recorded version is higher than this release knows is refused before any migration runs, so startup fails and readiness reports why. This happens after an image rollback: the newer release migrated the database, and the older one cannot know what the new schema means. The message tells the operator to run the release that migrated it or restore a backup.

Migrations own every constraint and index: CHECKs, unique keys, foreign keys and the FTS5 index with the triggers that keep it synchronized. `persistence/schema.ts` declares only what a query needs to be typed, which is each table's columns, types, nullability, primary key and defaults. `tests/server/persistence/schema-columns.test.ts` holds it to a fully migrated database: the declared tables must be exactly the migrated ones, and every declared column must match the migrated column. Constraints and indexes are not compared, since nothing in `schema.ts` states them. Nullability is compared only for columns outside the primary key, because SQLite reports a primary key column's `notnull` as 0 even when it cannot be null. The comparison leaves out `schema_migrations`, which is the runner's own ledger, and `feed_item_search` with its FTS5 shadow tables. That index is typed separately in `search/search-schema.ts`, outside `schema.ts`, because the column test covers ordinary tables only.

What this costs is that a new column is written twice, once in a migration and once in `schema.ts`. The column test is what catches the two drifting apart, and a constraint exists only in SQL, so a reader of `schema.ts` does not see it.
