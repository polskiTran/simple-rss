# Report a failed startup through readiness, and exit only when the running state is unknown

A startup failure does not end the process. `startService` (`src/server/service.ts`) builds every domain service inside one `try`/`catch`, and `compose` turns a failure into a `Startup` of kind `failed` with the step that failed as its reason: the database could not be opened, migrations failed, or a service could not start. The process still listens. `/health/live` stays green, `/health/ready` answers 503 with that reason, and every `/api` route answers 503 `unavailable`, so no request reaches a half-built installation. The only startup failure that rejects is a socket that cannot bind, and `main.ts` exits non-zero on it. The Setup Secret follows the same rule: `SETUP_SECRET` is optional in `config.ts`, and while the installation is unclaimed an absent or too-short secret is a readiness reason (`setupBlocker`), not a configuration error. Exiting was rejected because the platform restarts a container that exits: one with a bad volume, a failed migration or a missing secret fails again the same way and crash-loops, and the operator sees a restart counter and has to find the cause in the logs of a process that keeps dying. A process that stays up shows the cause at `/health/ready` and in one `startup.failed` log record. The cost is that a deployment can run while serving nothing, and only a health check on `/health/ready` notices.

Readiness checks three things in order, and stops at the first that fails (`readinessFailure` in `app.ts`). First the startup failure, since without services there is nothing else to check. Then a real write: `assertWritable` (`persistence/database.ts`) upserts the one row of `write_probe`, because a read-only or full volume opens without complaint and only fails on the first write. Reusing one row keeps the probe from growing the database. The Setup Secret is checked last, because whether it is still required depends on whether the installation is claimed, which needs the database.

The HTTP surface depends on registration order, and `createApp` registers it in an order that is part of the contract. `/health/*`, including a JSON 404 for an unknown health path, and every `/api/*` route, including a JSON 404 or the 503 above for anything unmatched, are registered before the static client fallback, so neither prefix can ever answer with the client's HTML. The `/api` guards (`sameOrigin`, then `requireSession`, ADR 0004) register before any route they protect. Whether the installation has services is decided once, when `createApp` runs, so no route asks per request.

Logs are structured JSON on stdout, one record per event, and a caller passes an event name (`server.started`) and fields, never a secret, a Session token, a Feed summary or Reader content. Each request produces one `request.completed` record with its method, path, status and duration. The query string is left out, because it carries search terms and signed image URLs. Health probes log at debug, so a platform polling readiness does not fill the log.

An error after startup is treated the opposite way to a startup failure. `main.ts` listens on `uncaughtExceptionMonitor`, which logs `process.uncaught_exception` or `process.unhandled_rejection` and leaves Node's default handler in place, so the process still exits non-zero. A startup failure is a known state: nothing is serving `/api`. An uncaught error is an unknown one, and a process that swallowed it would go on answering ready while serving state that may be corrupt. A restart from the database is the safer recovery.

Shutdown runs within the platform's grace period. On `SIGTERM` or `SIGINT` the scheduler stops taking work, the server stops accepting connections, and idle keep-alive connections are closed on a short interval rather than once, because a keep-alive socket only becomes idle after its response has flushed, and a single sweep would leave every connection that was still writing open until the grace period ended. After the server has drained, the process waits for in-flight polls, closes the Reader workers, and closes the database. Connections still open after `SHUTDOWN_GRACE_MS` (ten seconds by default) are closed, because a platform that sent `SIGTERM` sends `SIGKILL` next, and an orderly close of the database is worth more than one slow response. A second signal exits at once with status 1.
