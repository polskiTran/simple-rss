# Poll Feeds from persisted due times, and let only a publisher's answer change Feed Availability

Polling is in-process background work with no cron and no queue. Each Subscription stores its next due time, and `subscriptions/poll-scheduler.ts` `PollScheduler` wakes every minute, polls the most overdue Subscriptions in bounded batches, and keeps going while batches come back full (ADR 0007). Because due times are stored rather than held in timers, catching up after a restart or a deployment is the ordinary path, not a recovery step. Every poll goes through `subscriptions/feed-refresh.ts` `FeedRefresh`, which shares one in-flight poll per Feed, so a scheduled poll and the User's Refresh never retrieve the same Feed twice at once. The Retention sweep runs after each round of polls, never before them, so that what this wake observed counts before anything is judged expired.

Due times are spread on purpose. `subscriptions/polling-schedule.ts` adds to each due time an offset derived from a hash of the Feed's id, under a tenth of the interval and never more than fifteen minutes, so Subscriptions on the same Polling Interval do not poll in a burst, and the spread is the same after a restart. Changing the Polling Interval recomputes the due time from the last poll, or from when the Subscription began if it has never been polled: a shorter interval that is already overdue polls at the next wake, and a longer one waits out the rest of its time.

`subscriptions/feed-poll.ts` `FeedPoll` is the only writer of poll outcomes. A poll's writes, the Feed Window, a merge the retrieval revealed (ADR 0007), and the Feed Availability that `subscriptions/feed-availability.ts` `settle` decides, happen in one transaction, after the retrieval and the parse. That transaction first confirms the Subscription still exists, and writes nothing if it does not: unsubscribing takes effect at once, and a poll that was in flight when the User unsubscribed must not bring back what they let go of.

Feed Availability changes only on an answer from the publisher, or a failure to reach one. A success clears the failure run. A bad answer adds to the run and backs off, doubling the wait from the Polling Interval for each failure in a row up to one day, and never removes the Subscription; three in a row make the Feed `unavailable`, which outranks `unchecked`, so a Feed that has never answered and keeps failing is shown as unavailable. A poll this installation never sent, because Retrieval's gates were full (`busy`), leaves Feed Availability as it was and moves the due time one Polling Interval on. A poll that throws reaches no verdict either, so Feed Availability stays as it was, but its due time still moves one Polling Interval on, because a Feed that always throws would otherwise stay first among the due Feeds and starve every other one. A `cancelled` retrieval is not set aside here and counts as `unreachable`; the Reader's cooldown sets aside both `cancelled` and `busy`. The code does that today, and nothing here decides whether the difference is intended. Every network-level failure (an invalid or blocked address, an unresolvable host, a bad, looping, or overlong redirect chain, a connection that failed) is shown as the one category `unreachable`, because the finer distinctions are transport detail the User cannot act on; timeouts, size, content type, HTTP status, and an invalid Feed keep their own categories.

Feed URLs are logged as origin and path only (`subscriptions/loggable-url.ts` `loggableUrl`), because a Feed's query string can carry a private subscriber token.
