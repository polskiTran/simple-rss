# Load nothing from outside the installation

The browser contacts only the installation. The content security policy (`http/security-headers.ts`) allows scripts, styles, fonts, connections, and form targets from `'self'` alone, images from `'self'` and `data:`, no plugins, no `<base>`, and no framing by another page. The policy is the enforcement, not a convention: a publisher URL that reached the page by mistake would not load. Two consequences follow for what the client is built from. The typefaces ship inside the client bundle as files, and never as `data:` URLs: `font-src` does not allow `data:`, and the smallest subsets of the variable faces fall under Vite's 4 KB inlining limit, so `vite.config.ts` turns inlining off for font files (`assetsInlineLimit`). And every image a publisher supplies reaches the browser through the image proxy.

The API never hands the client a publisher's image URL. A Feed Item's own image is the same-origin path `/api/items/:feedItemId/image`, resolved on the server from the stored item, and an image inside Feed Content or an extracted Original webpage is a signed path, `/api/reader/image`, carrying the target, an expiry, and an HMAC over both. The proxy retrieves through `Retrieval` (ADR 0005) and accepts nothing else, so the publisher sees the installation's address and never the User's, their cookies, or the page they were reading. The rejected alternative, letting the browser load publisher images directly, would need `img-src *` and would tell every publisher with an image in a Feed when, and from where, the User read it.

A signed path lives two days (`READER_IMAGE_URL_LIFETIME_SECONDS`), under a key the process mints at startup. Signatures are made when a response is prepared, so the caching of each response is set against that lifetime. A Reader View item response, which signs its Feed Content images, is never cached, so reopening an item always gets fresh signatures without re-ingesting it. An extracted Original webpage is cached privately for one day (`READER_CACHE_SECONDS`), shorter than the signature lifetime, so a cached article's images still verify. A proxied image is cached privately for seven days (`IMAGE_CACHE_SECONDS`). A restart mints a new key, so an article the browser cached before it loses its inline images until it is extracted again.

The proxy answers every failure with the same `404 image_unavailable`: a missing, malformed, expired, or tampered signature, a refused destination, an unreachable publisher, and a body that is not an accepted image all look alike (`http/image-routes.ts`). An `<img>` cannot act on a reason, and a uniform answer tells a caller nothing about a target or a signature. The two exceptions name a wait, where trying later can succeed: `429 image_rate_limited` with `Retry-After` when the client's budget is spent, and `503 image_busy` when `Retrieval` has no capacity. What this costs: every image is a retrieval and its bytes pass through the server, and the proxy cannot say why an image failed, so that is read from the logs.
