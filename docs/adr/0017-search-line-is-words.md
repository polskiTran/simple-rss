# Read the search line as words, not query syntax

What the User types into the search line is words, and the server turns them into an FTS5 match expression itself (`wordsOf` and `matchExpressionOf` in `src/server/search/search-service.ts`). Each word becomes a quoted phrase, and every word must match. The last one matches as a prefix, so results follow the line as it is typed. Double quotes are removed from each word, and a word with no letter or digit in it is dropped. The tokenizer reduces such a word to nothing, so quoting it would hand FTS5 an empty phrase, and a line of only punctuation answers no results without running a query. FTS5's own operators (`OR`, `NOT`, `NEAR`, column filters, parentheses) are deliberately not offered: a word such as `or` or `title:` is matched as text, and no input can produce a syntax error. Search is for refinding (ADR 0009), and a line someone types from memory should not fail because it reads as syntax.

Feed Items match on their title, their summary and the effective title of their Feed. The Jump-to Group matches Subscriptions by effective title or domain, never by Feed Description, with the same words: every word must appear in the title or the domain, compared after folding case and stripping diacritics (`folded`), the way the index's `unicode61 remove_diacritics 2` tokenizer treats Feed Items. A search for `cafe` therefore finds a Subscription named `Café` as it finds a Feed Item titled so.

A result shows a snippet only when its summary matched. The title and the Feed's title are already in the result, so a fragment of either shows nothing new. FTS5's `snippet()` cannot say this on its own: it returns the column's opening tokens even when the match landed in another column. So the query asks a second question, a `bm25` weighted to the summary alone. BM25 is negative for a match, since FTS5 keeps every term's weight above zero, and exactly zero when nothing in the summary matched, so the snippet is kept only when that score is below zero.

The server, not the client, says where a result matched. A result's title and its snippet each arrive as text with the ranges the index matched in it, `[start, end)` in UTF-16 code units, and the client marks exactly those ranges. Re-reading the line in the client would mark what the server never searched (`--` in `c++ --`) and miss what it did (a prefix match on `c` marks `C` and `compilers`). The ranges come from FTS5's `highlight()` for the title and `snippet()` for the summary, called with two private-use characters, U+E000 and U+E001, as the open and close markers, which the service strips out while counting offsets. The tokenizer counts private-use characters as part of a word, so a Feed's text can carry them too. The stripped text must then equal the text shown, and when it does not, the field is shown with no marks rather than marks in the wrong place. The Feed's title is matched but never marked, so it stays plain text.
