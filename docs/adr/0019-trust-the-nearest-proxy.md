# Believe the forwarded headers of the nearest proxy only

The documented deployment (ADR 0002) puts the service behind the platform's proxy, which ends TLS and opens a new connection to the container. Every request therefore arrives from the proxy's address over plain HTTP, and the only record of the real client and the real scheme is in the headers the proxy adds. `TRUST_PROXY_HEADERS` decides whether those headers are believed, and it defaults to `true`. With it on, the client address is the rightmost `X-Forwarded-For` entry, the one the nearest proxy appended (`http/client-address.ts` `clientAddress`); every entry to its left arrived from the caller and is ignored, so a forged header can only spend the forger's own budget. With it off, or when the header is absent, the address is the socket's. That address keys the per-client budgets of the login limiter (ADR 0003) and the image proxy's limiter. The same switch governs `X-Forwarded-Proto`, which the same-origin check (ADR 0004) uses as the scheme the browser saw, because the request URL says `http:` behind the proxy while the browser's `Origin` says `https:`. A header that is believed for the address is believed for the scheme, on the same terms.

The default is `true` because the documented deployment is behind a proxy. Defaulting to `false` there would put every client in the proxy's one budget, so five wrong passwords from anyone would refuse the User, and the same-origin check would refuse every state change from an HTTPS page. What this accepts: a deployment exposed directly with the switch left on lets a caller rotate `X-Forwarded-For` to escape the per-client limit. The installation-wide limit does not read the header and still holds, and `docs/DEPLOYMENT.md` tells a directly exposed deployment to set `false`.

`Strict-Transport-Security` is sent on every response without looking at the scheme (`http/security-headers.ts`). Behind the proxy the service cannot tell an HTTPS visit from a plain one without trusting a header, and it need not: browsers ignore the header on a plain HTTP response, so sending it unconditionally is correct either way.
